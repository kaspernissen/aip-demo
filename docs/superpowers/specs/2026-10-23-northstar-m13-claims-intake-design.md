# M13: claims-agent becomes the intake agent

Date: 2026-10-23. Branch `m13-claims-intake`, from `m12-linkerd` at `76c7c85`.
Not run against the cluster; unit tests only.

## Why

claims-agent had no model: it parsed a JSON claim, delegated to settlement-agent
over A2A and parked the task at `input-required` while a human decided. The
question was what justifies A2A here. The answer: claims-agent takes the
customer's first notice of loss in their own words, and asks for what is
missing through A2A's own multi-turn `input-required` state, in the same task.
Plain REST has no "this request is waiting for you to say more" state.

## Decisions

- **Two paths in `_claim`.** Input that parses as a JSON object takes today's
  deterministic path, with no model. Everything else (prose, a malformed
  object, a bare number or list) is free text for the model.
- **The model reads, the code decides.** `extraction.py` runs a PydanticAI
  agent (`anthropic:claude-sonnet-5`, env `NORTHSTAR_CLAIMS_MODEL`,
  `defer_model_check=True`, `name="claims-agent"`, structured `IntakeDraft`
  output). `intake.check_draft` judges the draft through `validate_claim`, the
  JSON path's own validator, plus what a first notice of loss needs: a positive,
  finite euro amount, an ISO incident date that is not in the future, a
  description, and bounded lengths. A value that does not validate counts as
  missing. The model's own `missing` list never decides anything.
- **Currency.** Settlement has always been sent `EUR`. An amount in another
  currency is never converted: it counts as missing and the customer is asked
  for euro.
- **Claim id.** `CLM-INTAKE-` plus six upper-case hex digits, generated by the
  agent before the model runs. Never taken from the customer's text, so a
  customer cannot name someone else's claim. Baggage is set before the model
  call, so the `invoke_agent` and `chat` spans carry `northstar.claim.id`.
  `conversation_id` is the claim id.
- **Instrumentation.** `Agent(instrument=...)` does not exist at
  pydantic-ai-slim 2.42.0, so claims-agent's `bootstrap.py` copies
  settlement-agent's `Agent.instrument_all(InstrumentationSettings(include_content=capture_content_enabled(), version=5))`
  and adds `HTTPX2ClientInstrumentor` for the model's hop. A test holds the two
  copies code-identical. The capture switch is the same `NORTHSTAR_CAPTURE_CONTENT`.
- **A second reason to wait.** The agent writes
  `northstar.a2a.parked_reason` (`needs_information` or `awaiting_approval`)
  in task metadata when it parks. The resume path is chosen only from that
  key, never from the message. No key means the approval wait (every task
  parked before M13). An unknown value is refused and the task keeps waiting.
  Because a2a-sdk merges metadata, the approval park now writes its reason
  explicitly.
- **Intake state** (`northstar.a2a.intake_state`): claim id, the customer's
  messages (each capped at 2000 characters), the kept draft fields, and the
  count of questions asked. It is read only from metadata, never from history.
  Each round re-reads all of the customer's messages, with the previous draft.
- **The question.** The model words it only when its own `missing` list
  overlaps the code's (capped at 300 characters). Otherwise the code sends a
  fixed question for the first missing field. The status message carries the
  question as a plain text part, then the reply JSON (`status:
  needs_information`, `missing`, `question`) as the last part, where
  customer-ui and `delegation.py` look for it.
- **The cap.** At most 3 questions. If something is still missing after the
  third answer, the task fails politely. A model error fails the task with the
  reason in `error`, as a settlement failure does: an exception would drop the
  stream.
- **M10 rules.** `execute()` returns when parked. The information resume runs
  in a `northstar.a2a.resume` span that links to the parked span (`link.reason
  = resume`). Both waits set the span attribute `northstar.a2a.parked_reason`.
- **Delegation.** The payload to settlement-agent now carries `description`
  on both paths. settlement-agent's `_validate` ignores it, and a test shows it
  reaches neither the settlement model's prompt nor the payment system.
- **Pins.** `pydantic-ai-slim[anthropic]==2.42.0` and its transitive pins,
  copied exactly from settlement-agent. The claims-agent venv matches the pin
  file package for package. A test holds every shared pin equal across the two
  agents.
