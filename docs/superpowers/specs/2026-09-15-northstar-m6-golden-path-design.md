## 1. What changed since the M1 spec described M6

The M1 spec (`2026-09-07-northstar-m1-connected-design.md:48`) describes M6 as
**"Crossplane `Agent` CRD, Argo CD, Backstage template"**, with the line *"The
platform API is `Agent`. The rest is implementation detail."*

**M5's spec dropped Crossplane and Argo CD** (`:100`, `:318-325`) and reassigned
the platform-API role to the `FeatureFlag` resource M5 introduced: *"This
resource is the contract. It is the artifact a human edits, the diff a reviewer
reads, and — with Crossplane dropped from M6 — the object M6's Backstage will
put a UI on."*

This design follows M5's revision. The reason is the one M5 already argued and
this milestone should not re-litigate: a Crossplane `Agent` CRD composing the
existing Deployments would be a **wrapper over things that already work**, and
the honest platform-API story is already told by a resource a human edits that
changes a real decision with no redeploy. Adding a second CRD layer over it
would make the demo longer and the claim weaker.

**Consequence, and it is the first thing M6 must fix.** Seven committed
documents still describe the Crossplane version and they now contradict this
design:

## 2. Scope — what M6 builds

Chosen with Kasper 2026-09-15 from three options, explicitly **not** the full
golden path:

**In:**
1. **Backstage deployed at stage 6**, in-cluster, reachable through
   `start-demo.sh` like every other surface.
2. **A software catalog covering all eight components** — `claims-agent`,
   `settlement-agent`, `customer-ui`, `reviewer-ui`, `eval-scorer`,
   `policy-decision-service`, `payments-api`, `payments-mcp` — with the agent
   cards in `contracts/agent-cards/` linked as the reviewable interface
   definition they already are.
3. **The Kubernetes plugin**, so each catalog entry shows its live workload.
4. **An autonomy card that reads the contract live and can change it** — the
   `FeatureFlag` `northstar-autonomy`, per agent identity. This is the milestone's
   point: the same one-word flip M5 proved, performed from a UI instead of
   `kubectl`, against the same resource, with the same audit trail.

**Out:**
- **The scaffolder template that generates a new agent.** It is the other half of
  the M1 spec's claim, and it needs a publish target — Backstage's scaffolder
  publishes generated code to a git repo, and **this repo has no remote**
  (raised twice, deferred twice; not M6's fight). Deferred with the reason
  recorded, not rejected.
- **Crossplane and Argo CD** — see §1.
- **Authenticating the human.** M3's carried limitation, still untouched. The
  autonomy card writes as Backstage's own service account, which means
  **Backstage becomes a new privileged writer in this cluster** — see §4.
- **TechDocs.** No documentation pipeline; the catalog links to the repo's
  existing markdown.

## 3. The shape

Backstage is a Node application, scaffolded once with `@backstage/create-app`
and committed under `platform/backstage/`. It is built into
`localhost:5001/northstar/backstage:dev` by the existing
`scripts/rebuild-and-deploy.sh` machinery and runs as one Deployment in
`northstar-platform`.

**SQLite, not PostgreSQL.** Backstage defaults to an in-memory/SQLite catalog for
development and PostgreSQL for production. This is a demo cluster that is torn
down and rebuilt; a second stateful component buys durability nobody wants and
costs a pod, a PVC and a failure mode on stage. The catalog is re-read from
committed `catalog-info.yaml` files on every start, which is the property that
actually matters here: **the catalog is derived from the repo, not from a
database somebody edited once.**

**Static catalog locations, no git discovery.** With no remote, the catalog
reads `catalog-info.yaml` files from the image's own filesystem. That keeps the
"catalog is derived from committed content" property and removes a network
dependency from the demo path.

## 4. The security boundary, and why this task gets a review

**Backstage will hold a Kubernetes ServiceAccount that can PATCH
`featureflags.core.openfeature.dev`.** That is a genuine new privilege in a
cluster whose entire thesis is least privilege and workload identity, and it is
the one part of M6 that can make the demo *worse* if done carelessly.

Requirements, all of them testable:

- **The Role is namespaced and resource-named.** `patch`/`get`/`list` on
  `featureflags`, in `northstar-platform`, restricted by `resourceNames` to
  `northstar-autonomy` alone. Not `*`, not cluster-wide, not other verbs.
  **No `delete`.** No access to Secrets, ConfigMaps or Deployments beyond what
  the read-only Kubernetes plugin needs.
- **The Kubernetes plugin's read access and the contract card's write access are
  two different ServiceAccounts**, so "Backstage can see the cluster" and
  "Backstage can change policy" are separate grants that can be reasoned about
  and revoked independently.
- **The write path is auditable.** A change made from Backstage must be
  distinguishable in telemetry from one made with `kubectl` — otherwise the
  audit trail M3/M4/M5 built gets a hole punched in it by a convenience UI.
- **The PDS remains the decision point.** Backstage changes the *contract*; it
  never decides anything. Nothing in M6 may give Backstage a path to influence a
  policy decision other than by editing the resource the PDS already reads.

**This inverts M5's demo risk.** M5's risk was that the flip did nothing (a
vacuous demo). M6's risk is that the flip is too easy — an unauthenticated UI in
the cluster that can lower a guardrail is a worse story than no UI. §10 records
this as the known limitation rather than dressing it up.

## 5. What must be true for the demo to work

1. Backstage comes up at stage 6 and is reachable via `start-demo.sh`.
2. All eight components appear in the catalog, each derived from a committed
   `catalog-info.yaml`, each showing its live workload.
3. The autonomy card shows `assisted` for both identities on a freshly built
   cluster — **the contract ships refusing** (M5-R8), and M6 does not change that.
4. Changing `settlement-agent` to `autonomous` from the card causes the *same*
   observable outcome M5 proved from `kubectl`: a settlement that was refused is
   executed, with no redeploy.
5. **The anti-vacuity control still holds.** M6 adds a second way to change the
   contract; it must not add a way to *appear* to change it. The e2e must fail if
   the card's write does not actually reach the resource.
6. Reverting from the card returns the cluster to its refusing state.

## 7. The process, deliberately leaner than M5

M5 took six tasks, two opus escalations and a 16-finding whole-branch review.
M6 is four tasks. Kasper's standing instruction is that this has taken too long,
so:

- **Sonnet by default.** Opus for Task 3's review only — it is the security
  boundary in §4 — and for the whole-branch review.
- **Task reviews on Task 3 only.** Tasks 1, 2 and 4 are covered by the
  whole-branch review, per the lean default.
- **One gate run, and it runs AFTER the whole-branch review's fix wave.** This is
  M5's most expensive lesson (M5-R38): M5 ran its gate before the review, the
  review's wave changed twelve `GATE_PATHS` files, and the milestone merged on a
  `PREDICTED` row. M6 does not repeat it.

## 9. Memory

Measured 2026-09-15 before planning: Docker has **29.08 GiB** available and the
cluster is using **5.74 GiB** across 34 pods. Backstage is one Node process with
no database. The M1 spec's "~9–10 GB by M6" budget is not at risk, and the
`~8 GB` stage rows in that spec's table remain the right order of magnitude.
Re-measure after Task 1 rather than carrying this figure forward.

## 10. Known limitations, stated plainly

- **Backstage is unauthenticated.** Anyone who can reach the port can lower the
  autonomy guardrail. Acceptable for a laptop demo cluster reached through an
  explicit `kubectl port-forward`; it would not be acceptable anywhere else, and
  the talk should say so rather than let the audience assume otherwise.
- **No scaffolder**, so the M1 spec's *"the rest is implementation detail"* claim
  is only half-demonstrated: the platform API is shown as a real object with a
  real UI, but nothing generates a new agent from it.
- **The catalog is static.** It reflects committed `catalog-info.yaml` files, not
  a discovered repo, because there is no remote to discover.
- **The write credential's real cost (M6-R10).** §4 asks for "two different
  ServiceAccounts" so the read grant and the write grant are separately
  revocable, and that half is real — measured live, revoking one does not
  touch the other. What that requirement does **not** buy, and what the
  Task 3 review measured directly by decoding both tokens in the running
  pod, is a matching **credential mechanism**: the write grant's token is a
  legacy Kubernetes **Secret-based service-account token** — no `exp`, no
  `aud`, no binding to the pod or the Secret object — mounted read-only
  alongside the pod's own kubelet-projected, expiring, audience-bound
  read-only token, in the **same single Node process** that also runs the
  scaffolder (23 actions), techdocs, the proxy and mcp-actions, all under
  guest auth and an allow-all permission policy. A compromise of that one
  process is therefore a **durable, unbounded policy-write credential** —
  the more dangerous grant got the *weaker* mechanism, not a matching one.
  It survives the pod being deleted and the image being fixed; the only
  revocation is deleting the Secret/SA/RoleBinding, and nothing here
  monitors for that. The separation between "the read-only code path" and
  "the write code path" picking up the wrong token is a code convention
  inside one process, not an isolation boundary between two. The reviewer
  found no concrete guest-reachable file-read primitive in the enabled
  plugin set, and does not claim an exploit — but the honest statement of
  the trade-off is: **the structural fix (a separate Deployment running as
  `backstage-autonomy-writer`, called over HTTP, so a Backstage compromise
  yields the ability to *ask* rather than a credential to *keep*) was not
  built.** It is carried as recorded debt, deliberately, because Kasper is
  time-pressured and M6 is scoped lean — not because the trade-off was
  judged acceptable on its merits. `deploy/k8s/backstage.yaml`'s own
  comment on the Secret states only the favourable half of this (the RBAC
  is narrow); this paragraph is the rest.
- **The auditability claim is weaker than it reads.** §4 requires the write
  to be "distinguishable in telemetry from one made with `kubectl`." It is —
  but not durably, and not through the signal the code comments used to
  lean on. `metadata.managedFields` (the `fieldManager` mechanism) records
  **current ownership of a field, not a history of who has touched it.**
  Measured directly: before the card's write, the targeting field's
  `managedFields` entry was owned by `manager: kubectl-patch`; after the
  card's write, that entry is gone and only `manager:
  backstage-autonomy-card` remains. A subsequent `kubectl patch` of the
  same field is symmetric — it erases the Backstage entry in turn. So
  `managedFields` is a point-in-time confirmation of who wrote a field
  *last*, not a durable audit trail, and a `kubectl` revert of a card-made
  change leaves no `managedFields` trace that Backstage was ever involved.
  The durable record is the **OTLP span**
  (`northstar.autonomy_contract.change`), which does reach Jaeger and
  OpenSearch and is the signal to point an audience at; the Backstage
  `auditor` event is real but lives only in this pod's own logs, with a
  `:memory:` database and no log shipping. (Task 4's e2e should assert the
  span lands, the way `test_opensearch_trace_ingest.py` already does for
  `policy.decision` — nothing today does for this span.)
