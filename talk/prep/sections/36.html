So who runs those checks? An open-source evaluator called AgentEvals. Think of it as an auditor that reads the agent's work after the fact. Follow the arrows.

The agents emit spans, as always. Nothing is added for the auditor. The Collector already sends every span to Jaeger; it sends AgentEvals a copy. AgentEvals files every trace of one claim together and runs our five checks. And the grade goes back as telemetry, on the agent's own span.

It closes Prove and Kasper's half. It shows the evaluation loop end to end and makes the architectural point: evaluation is a consumer of standard telemetry, not an SDK inside the agent. The panel is real output (scripts/demo evidence, CLM-INTAKE-B1BEF0, 2026-10-27). It also answers the auditor's fifth question in part: the grade is itself a record, in the same pipeline.

The theory behind it

Plain words. The agent writes its diary (spans). The Collector photocopies the diary for the auditor. The auditor reads it, writes its marks on sticky notes, and posts them back to the same filing cabinet, attached to the right page. The agent never knows the auditor exists, so it can't behave differently while being watched.

Sessions. AgentEvals groups spans into sessions by gen_ai.conversation.id. Both agents set it to the claim id, so one session = one claim, spanning intake and settlement, across traces.

The grade's shape. One gen_ai.evaluation.result log event per check, attached to the operation it judged, with name, score, label and (enabled here) an explanation. That's the primary form in the GenAI conventions, so any backend that reads OpenTelemetry logs can show the grade beside the work.

What it can't see. Only the agent's own GenAI spans: tool calls, results, final answer. Not the policy decision, the human's approval or the caller's identity. That side is read in Jaeger and with demo evidence. So the two halves are complementary: the platform's spans prove what was allowed; the agent's spans, graded, show what it attempted.

Configuration and options

  • deploy/observability/agentevals.yaml: image ghcr.io/agentevals-dev/agentevals:0.11.0, agentevals serve with OTLP HTTP on 4318 and gRPC on 4317, UI/API on 8001 (kind host port 18001). AGENTEVALS_EVALUATION_EVENTS=true and …_EXPLANATION=true turn on the write-back. OTEL_EXPORTER_OTLP_ENDPOINT points back at the collector.
  • Collector: an otlp_http/agentevals exporter on the traces pipeline, with sending queue and retry.
  • When checks run: the demo driver triggers them. scripts/demo evidence POSTs to /api/streaming/evaluate-sessions with the five code evaluators (judge model in config.judge_model, 60 s timeout for prompt_injection). scripts/demo evals adds the built-in judged metrics.
  • Where the grade lands: the event goes to the collector's logs pipeline, which exports to Weaver live-check and, with the Dash0 overlay enabled (DASH0_AUTH_TOKEN set), to Dash0. Jaeger is traces-only, so it doesn't show the events.
  • Label quirk (0.11.0): the event label is fixed to pass | fail | not_evaluated, so a flag reads fail; the explanation and scripts/demo say "flagged".

If someone asks

Does the evaluation slow the payment down?
No. It runs after the fact, off a copy of the spans. It blocks nothing.
Is gen_ai.evaluation.result the standard shape?
Yes, the primary form of the convention: a log event with name, score and label, attached to the operation it judged.
