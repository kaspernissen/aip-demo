The passport, in config

WILLIAM

Here's the passport office's rule, as config. One object, a ClusterSPIFFEID.

[point at the template]

The ID is a template: the trust domain, then the pod's namespace, then its service account. Where it runs. And the pod selector says which pods get this passport: the settlement agent.

Nothing the agent says goes into it. Not its name, not its card, not its prompt. If you want a different passport, you have to run somewhere else, and that's a deploy, which goes through review.

The gateway reads this passport on every call. You'll see it in Kasper's trace, as the caller on the decision.

Built from where the pod runs, not from what the agent says.

What the slide is for

Slide 13 explained the idea; this one shows that it's a few lines of declarative config, not a project. It plants the exact string the audience will see again four times: in the gateway's CEL rule (slide 16), in the flag's targeting (slide 18), as caller identity on every claim in demo step 4, and in the decoded SVID on "What you just saw" (slide 24).

The theory behind it

Plain words. A registration entry is the passport office's rulebook: "a pod in this namespace, running as this service account, gets this ID." The SPIRE controller manager watches pods, and for every pod the ClusterSPIFFEID selects, it writes a registration entry into the SPIRE server. When that pod later asks the node agent for an SVID, the agent attests it (kernel → kubelet → namespace and service account), finds the matching entry and returns a signed document.

Why namespace + service account. Both are set by whoever deploys the pod, and both are protected objects. The keystone (slide 19) denies an agent identity any write to pods, deployments, service accounts' tokens, RBAC, and the spire.spiffe.io CRDs. So an agent can't move itself into another namespace, run as another service account, or edit this registration.

Configuration and options

# deploy/platform/spire/registration.yaml (one of several)
kind: ClusterSPIFFEID
metadata: { name: northstar-settlement-agent }
spec:
  className: northstar-platform-spire
  spiffeIDTemplate: "spiffe://{{ .TrustDomain }}/ns/{{ .PodMeta.Namespace }}/sa/{{ .PodSpec.ServiceAccountName }}"
  podSelector:       { matchLabels: { app: settlement-agent } }
  namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: northstar-agents } }
  workloadSelectorTemplates:
    - "k8s:ns:{{ .PodMeta.Namespace }}"
    - "k8s:sa:{{ .PodSpec.ServiceAccountName }}"
  fallback: false
  • One object per workload: settlement-agent, claims-agent, reviewer-ui, agentgateway and the policy decision service each get their own, each pinned to its namespace with namespaceSelector, so a pod with the same label in another namespace gets nothing.
  • className ties the object to this SPIRE install's controller manager; another SPIRE in the cluster ignores it.
  • fallback: false: this entry is not a catch-all default for pods nothing else matches.
  • Hardening knobs not used here: add k8s:container-image or a pod-label selector to workloadSelectorTemplates; set dnsNameTemplates for X.509 SVIDs; federate trust domains with ClusterFederatedTrustDomain for cross-cluster calls.

The resulting ID for the settlement agent is spiffe://northstar.local/ns/northstar-agents/sa/settlement-agent. Its audience when calling the gateway is spiffe://northstar.local/ns/northstar-platform/sa/agentgateway.

Alternatives

  • Static registration entries (spire-server entry create or ClusterStaticEntry): explicit, but they don't follow pods as they scale.
  • A different path scheme: some teams encode the app or the environment instead of the service account. The ns/sa scheme matches what Istio uses, so IDs stay readable across meshes.
  • No SPIRE at all: projected ServiceAccount tokens with an audience give a similar "who is calling" claim, without node attestation.

If someone asks

Could someone label their own pod app: settlement-agent?
Only in northstar-agents, the namespace selector requires it, and it would still need the settlement-agent service account to get that ID. Creating pods in that namespace is a deploy-time permission no agent holds, and the keystone denies it to agent identities even if RBAC is loosened.
Where's the agent's key?
There isn't one in the pod. The SVID is fetched over the Workload API socket that the SPIFFE CSI driver mounts, and the socket only ever answers with the identity of whoever is calling it.
