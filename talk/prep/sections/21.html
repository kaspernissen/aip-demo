This is Northstar, a made-up motor insurer. All of it runs in a kind cluster on this laptop.

[point left to right along the boxes]

A customer describes what happened in their own words, in the customer UI. The claims agent sends those words to a model, Claude, which turns them into a claim: amount, policy, date. The claims agent decides nothing about money. It hands the claim to the settlement agent over A2A. The settlement agent has a model too. It proposes the payment, and to pay it calls agentgateway over MCP. It never calls the payment tool directly.

The gateway checks who is calling, enforces the ceiling, and asks the policy service whether this payment is allowed. The policy service reads the autonomy flag. Only on a yes does the call go on to payments-mcp and the ledger. And note the dashed line at the top: the model calls go through the same gateway, and the API key lives there, not in the agents.

[point at the two bars at the bottom]

Underneath, Linkerd and network policy make the gateway the only road to the tool. And every service reports to one OpenTelemetry Collector, at one hundred percent, with no sampling.

If this looks familiar, it's William's deterministic spine, built: the agent proposes, the platform decides, a gate pays.

The theory behind it

Separation of duties between agents. The claims agent turns free text into structured data. The settlement agent decides what to propose. Neither can move money. In banking terms that is a maker/checker split before a human ever appears, and it narrows what an injection can do: the model that reads the customer's words is not the one holding the payment tool.

A single enforcement point. Every policy architecture separates the place that enforces (the Policy Enforcement Point, here agentgateway) from the place that decides (the Policy Decision Point, here the policy decision service, PDS). The enforcement point is only worth something if nothing can go around it. That is why the bottom bar matters: Linkerd admits only the gateway's mTLS identity into payments-mcp, and NetworkPolicy gives the agents no route out except to the gateway.

Namespaces as trust zones. The four coloured areas are Kubernetes namespaces: northstar-agents, northstar-platform, northstar-tools, northstar-systems. The agents' SPIFFE IDs and the keystone policy both key on the namespace, so a namespace is a security boundary here, not just a folder.

Alternatives

  • One agent instead of two. Simpler, but the model that reads untrusted customer text would then also hold the payment tool. Two agents show A2A and make the hand-off a traced, governed hop.
  • Agent calls the tool directly, with a library-level check. Works until someone forgets the check. A gateway is enforcement the agent's code cannot skip.
  • A different gateway (Envoy with ext_authz, Kong, an API gateway with an OPA plugin). They can authorize HTTP, but agentgateway parses MCP, so a rule can name mcp.tool.name and mcp.tool.arguments.amount.

If someone asks

Is this a real insurer's architecture?
No. It is a reference demo, small enough to run on a laptop, built so each guardrail and each trace hop is visible. The shape (intake, proposal, gated execution) is a common one for regulated payout flows.
Why does the model call go through the gateway too?
So the agents hold no API key and have no route to the internet. The gateway's span records which agent called which model under its SPIFFE identity.
What happens if the PDS is down?
The gateway's guardrail is failureMode: failClosed: no answer means no payment.
