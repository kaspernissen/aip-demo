The model, through the same door

WILLIAM · starts 11:35 · 40 s · Ring 2 · per call

Manuscript

WILLIAM

The same gateway has a second door: the model. Every model call from both agents goes through it.

Three checks again. The passport: no SPIFFE token, 401. One rule: only the claims agent and the settlement agent may call a model at all. Anything else, even with a valid passport: 403. Then a list of models: ask for one that isn't on it, 404, and the request never leaves the cluster.

[point at apiKey]

And the API key lives here, in the gateway, read from a mounted secret. The agents hold none, and the network policy gives them no road to the internet. So the gateway's span says which agent called which model, and what it cost, under the same passport.

The agent holds no key. The platform does.

What the slide is for

Model traffic is the other half of what an agent can do. Without this slide the audience might assume agents call a model provider directly with a key in an environment variable. That key would be a credential the agent holds, and the model would be a road out of the cluster. This slide closes both and ties the model call to the same identity as the tool call.

The theory behind it

Plain words. A shared API key is a password everyone in the building knows. Move it into the gateway and the agents stop holding a secret at all: they prove who they are with their passport, and the gateway makes the call on their behalf. Rotate the key in one place; revoke one agent by removing it from one list.

Why this matters for evidence. The provider only sees "the gateway". The gateway sees which SPIFFE ID asked, which model, how many tokens. Its span carries the same gen_ai.* names as the agent's own chat span, plus jwt.sub and cost, so per-agent spend is a query, not a guess.

Three answers, measured on the cluster (2026-10-28). No token: 401 "no bearer token found". reviewer-ui with a valid SVID: 403 "authorization failed". An unlisted model: 404 model_not_found.

Configuration and options

# deploy/platform/agentgateway/config.yaml, the llm block (port 4000)
llm:
  port: 4000
  policies:
    jwtAuth: { mode: strict, … same issuer and audience as the MCP route }
    authorization:
      rules:
      - allow: 'jwt.sub in [".../sa/claims-agent", ".../sa/settlement-agent"]'
  models:
  - name: claude-sonnet-5
    provider: anthropic
    params: { apiKey: { file: /etc/agentgateway-model/ANTHROPIC_API_KEY } }
  • The key comes from the northstar-model Secret in northstar-platform, mounted as a file and read once at startup. Rotating it needs a gateway restart. setup-kind.sh prints ANTHROPIC_API_KEY: SET/EMPTY; empty means every pod comes up Running and the first claim fails at the model call.
  • The agents send Authorization: Bearer <JWT-SVID> (agents/settlement-agent/model_client.py), audience from NORTHSTAR_GATEWAY_AUDIENCE; a wrong audience is a 401.
  • Network: the agents' egress policy allows agentgateway on port 4000 and no ipBlock to the provider.
  • Options not on: agentgateway ships prompt guards for model traffic (regex and PII rules, a webhook, hosted moderation services), rate limits and token budgets, and multiple providers with failover. Northstar turns none of them on; the injection is caught after the fact by AgentEvals (slide 36).

Alternatives

  • LiteLLM: model proxy strongest on routing, budgets and cost tracking; virtual keys rather than workload identity.
  • Agent Router (formerly Envoy AI Gateway): Envoy-based LLM and MCP gateway in AAIF.
  • Kong AI Gateway, or a cloud provider's own gateway (Bedrock, Vertex) with workload identity federation.
  • Key per agent in a Secret: simplest, but the agent holds a credential and needs an internet route; one leaked key bypasses every check here.

If someone asks

Does the gateway read the prompt?
It can, with prompt guards. None are on in Northstar. The tricky claim's injection is flagged afterwards by the prompt_injection evaluator in AgentEvals.
Don't I double-count tokens now?
Yes, if you sum across every span: the agent's chat span and the gateway's span both carry usage. Pick one source.
Why 404 and not 403 for an unknown model?
That's agentgateway's answer when no model in the list matches. The request never leaves the cluster either way.
Verify before the talk The model name on the slide (claude-sonnet-5) matches what config.yaml and the agents request on the day.
