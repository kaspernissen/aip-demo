Everything in that evidence is OpenTelemetry, so first the thousand-mile view.

Two words before the picture. A span is the record of one step, like one tool call. A trace is every span of one run, held together by one trace id that every hop passes on, through MCP and A2A too.

[left boxes]

On the left, where telemetry is born. Instrumentation: the OpenTelemetry API and SDK in our own code, and auto-instrumentation for the frameworks we didn't write. And infrastructure: Kubernetes, and here the Linkerd proxies, which emit spans of their own.

[middle]

All of it goes to one place, the OpenTelemetry Collector. It receives traces, metrics and logs, processes them, and exports them to whatever backend you choose. Here that's Jaeger for traces, Prometheus for metrics, and Dash0 for all three. Analysis tools sit on top of the backends.

"Generate once, send anywhere. The backend is a choice, not a rewrite."

Keep five words: span, one step. Trace, one run. Propagation, the id passed hop to hop. Link, two traces joined. Names, what each attribute means. Each of the next slides is one of them. The claim crossed two protocols on its way. Here they are.

What the slide is for

Part of the audience has never worked with OpenTelemetry. This slide gives them just enough vocabulary to read the next five slides, and gives everyone the architectural point: instrumentation and backend are decoupled by an open protocol (OTLP) and a vendor-neutral pipeline (the Collector). The "five words" are the outline of the rest of the Trace section: span (26), propagation (29), trace (30), link (31), names (32).

The theory behind it

Plain version. Think of a parcel tracking system. Every depot that touches the parcel scans it (a span). The tracking number (the trace id) is printed on the parcel and read at every depot (propagation). All scans with the same number make up the journey (the trace). The Collector is the sorting centre: every depot sends its scans there, and it forwards them to whoever needs them.

The pieces.

  • API and SDK. The API is what code calls to create spans and metrics; the SDK is the implementation that batches and exports them. Libraries depend only on the API, so they stay silent until an application installs an SDK.
  • Auto-instrumentation. Instrumentation libraries that wrap frameworks (HTTP clients, ASGI servers, PydanticAI, the MCP SDK) and create spans without changing application code.
  • OTLP. The OpenTelemetry Protocol, over gRPC (port 4317) or HTTP (4318). Every service in Northstar speaks it.
  • The Collector. A pipeline of receivers, processors and exporters, defined per signal. It can batch, enrich, filter, redact, and fan out to several backends at once.
  • Semantic conventions. Agreed names for attributes (http.request.method, gen_ai.request.model), so a backend can understand data from any source.

Configuration and options

# deploy/observability/collector-config.yaml (condensed)
receivers:  otlp (grpc 4317, http 4318, CORS for localhost:8080),
            prometheus/spire (scrapes SPIRE server/agent metrics)
processors: resource_detection (env), batch (1s)
pipelines:
  traces:  otlp -> jaeger, weaver live-check, agentevals, debug
  metrics: otlp + spire -> prometheus (OTLP), weaver, debug
  logs:    otlp -> weaver, debug
  • No sampler in any SDK or in the collector: every span is kept.
  • The browser exports OTLP/HTTP directly to the collector; that is why the receiver lists http://localhost:8080 in allowed_origins.
  • Dash0 is an overlay (collector-dash0-overlay.yaml) passed as a second --config when DASH0_AUTH_TOKEN is set. It adds one exporter to each pipeline; no processor renames anything, so Dash0 gets the same names Jaeger does.
  • Linkerd proxies export OTLP/gRPC to the collector over mTLS, with no sampling of their own: a proxy span exists only for a request whose incoming traceparent is sampled.
  • Options not used here: tail sampling, attribute redaction (e.g. to strip message content before a backend), a gateway/agent collector topology.

Alternatives

  • Vendor agents and SDKs: often richer out of the box, but each backend change means re-instrumenting.
  • Export directly from SDK to backend, no collector: fewer moving parts, but no central place to fan out, redact or buffer, and every service needs backend credentials.
  • Other pipelines (Fluent Bit, Vector) can carry OTLP, but the Collector is where OpenTelemetry's own processors and receivers live.

If someone asks

Why Jaeger and not Tempo?
Either works; it's one exporter. Jaeger v2 is itself built on the Collector, and its UI is simple to show on stage.
What does 100% cost in production?
More storage and network. For decision spans in a regulated flow, the absence of a span is evidence, so dropping any of them breaks the audit. You can still sample high-volume, non-decision traffic separately.
Logs, too?
Yes, the logs pipeline carries AgentEvals' gen_ai.evaluation.result events to Weaver and, with the overlay, to Dash0.
