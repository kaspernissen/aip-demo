One trace id, every hop

KASPER · starts 27:15 · 45 s

Manuscript

KASPER

One trace id, carried across every hop. Read it top to bottom; it's the claim's path.

The browser starts the trace and sends traceparent as an HTTP header, and the claim id rides along as baggage.

Claims agent to settlement agent is A2A. The traceparent is in the header, but the A2A SDK doesn't read it, so we do it ourselves.

Settlement agent to the gateway is MCP. The id goes in the message itself, params underscore meta, the convention MCP adopted, and in the header too.

The gateway asks the policy service over a gRPC hook and forwards the traceparent, so the policy decision lands in the same trace. Then on to the tool and the ledger: MCP, then plain HTTP.

The one hop that can't be one trace is the person. Someone approves minutes later, so that's a new trace, with a span link back. And underneath it all, Linkerd's proxies add their own spans to the same trace.

"Drop the id at one hop, and the story falls apart."

What the slide is for

It shows that "one trace" is engineering work, hop by hop, and that each protocol carries the id differently. Platform teams will own this plumbing, so the honest gaps (A2A SDK, gateway ingress) are part of the message: propagation is not free just because every component "supports OpenTelemetry".

The theory behind it

Plain version. Propagation is passing the tracking number to the next depot. If one depot forgets to read it, it starts a new number and the parcel's journey splits in two. Nothing errors; you just get two half-stories.

W3C Trace Context. The traceparent header is 00-<32 hex trace id>-<16 hex parent span id>-<flags>; the last byte's sampled bit tells downstream services to record. tracestate carries vendor data. W3C Baggage carries application key-value pairs (here, only the claim id) across the same hops.

Linkerd. Each meshed hop adds four proxy spans (outbound server and client on the caller's proxy, inbound server and client on the callee's). The proxies only join traces whose incoming traceparent is sampled; they never start one. In the measured Large-claim trace, 148 of 304 spans were linkerd-proxy.

Configuration and options

# deploy/platform/agentgateway/config.yaml
mcpGuardrails:
  processors:
  - kind: remote
    host: policy-decision-service...:9100
    requestHeaders:
      allowed: ["traceparent", "tracestate"]
frontendPolicies:
  tracing: {randomSampling: true, parentNotSampled: true}
  • Proxy tracing is enabled in deploy/platform/linkerd/values.yaml.
  • Baggage is read by a BaggageSpanProcessor whose predicate admits only northstar.claim.id; ALLOW_ALL_BAGGAGE_KEYS is deliberately not used.
  • The browser helper must be a static import: under ZoneContextManager, an await before reading the active span loses it.

Alternatives

  • Put the trace id in the message body yourself (an application field): works over any transport, but every service has to know your convention and no library will pick it up.
  • Correlate by claim id only, no propagation: you can find all records of a claim, but you lose the parent/child causality that shows which call caused which.
  • Let the mesh create the trace: Linkerd won't start traces, and a mesh can't see inside MCP messages anyway.

If someone asks

Does agentgateway support SEP-414?
On egress, yes: it stamps _meta on what it forwards. On ingress it reads only the HTTP traceparent header. A client that carried context only in _meta (stdio, or uninstrumented HTTP) would fragment the trace at the gateway.
Why not make the human approval part of the same trace?
The wait can be minutes or hours with nothing running. A parent span spanning that time misstates duration and what was executing. Slide 31.
What is SEP-414?
The MCP spec enhancement proposal that defines W3C trace context in params._meta, so context travels with the message on any transport.
Verify before the talk "An upstream gap we filed" (A2A SDK): the repo lists it as filing-ready (docs/upstream-findings.md Finding 1), not filed. File it, or say "an upstream gap".
