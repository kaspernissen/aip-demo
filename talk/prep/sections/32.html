Our own names, as a contract

KASPER · starts 29:30 · 55 s

Manuscript

KASPER

Every name in that trace comes from somewhere. The semantic conventions name the common things: http-dot-something for web calls, gen_ai-dot-something for model and agent calls.

But a policy decision, a human review, an autonomy level: those names are ours. No convention covers them. So we write them down, in Weaver, OpenTelemetry's own tool for this.

[the four icons, left to right]

Define them in YAML, on top of the official conventions. Check the registry in CI. Generate the docs from it. And live-check: the Collector sends Weaver a copy of everything the cluster really emits, and it fails if we emit one of our names that we never defined.

"Telemetry names are an API. Weaver checks the API against what really runs."

So the record is complete, and its names are checked. Last word: Prove. Who grades the agent?

What the slide is for

It closes the Trace section by answering a question an auditor would ask about the evidence itself: how do you know the fields mean what you say? It's the fifth OpenTelemetry word: names. The audience should leave seeing attribute names as a contract with consumers (dashboards, alerts, evaluators, auditors), not as free text a developer picks on the day.

The theory behind it

Plain words. If one service writes policy.decision and another policyDecision, every query and alert silently misses half the data. Semantic conventions are OpenTelemetry's shared dictionary. Weaver is the spell-checker for your own additions to it. Think of an API schema (OpenAPI) for telemetry: the producer and every consumer agree on names, types and allowed values.

Why our own namespace. The repo's governing rule (docs/telemetry-contract.md): use what frameworks emit, instrument only our own code, and where a convention gap exists, report it upstream rather than papering over it. Names this project defines are prefixed northstar. so a reader sees at a glance which attributes a framework emitted and which we chose. There is no OpenTelemetry convention for a policy or autonomy decision (Gap 3 in the contract), so the decision span is ours, defined in the open.

The four steps, precisely.

  1. Define: telemetry/registry/ holds manifest.yaml (registry northstar, depends on semantic-conventions v1.44.0) plus claim.yaml, contract.yaml, policy.yaml, review.yaml, metrics.yaml. Everything is stability: development.
  2. Check: scripts/check-registry.sh runs otel/weaver:v0.28.0 registry check -r telemetry/registry.
  3. Generate: the same script runs registry generate … markdown and fails if the generated region of docs/telemetry-contract.md is stale, so the docs can't drift from the registry.
  4. Live-check: a weaver-live-check Deployment in observability, fed by the collector's otlp_grpc/weaver exporter (traces, metrics and logs), policy in telemetry/live-check.toml with fail_on = "violation".
- id: northstar.policy.decision
  type:
    members:
      - {id: permit, value: permit}
      - {id: deny,   value: deny}
  brief: What the policy-decision-service decided.

Configuration and options

  • Findings policy. Most traffic live-check sees is not ours (semconv, Kyverno, Linkerd, SPIRE, agentgateway). Those findings stay at information. For northstar.* names, missing_attribute and undefined_enum_variant are raised to violations. Overrides are first-match-wins, so the specific rule comes before the catch-all.
  • What live-check does not catch (v0.28.0, measured): a missing required attribute (a mutation dropping northstar.policy.rule survived), and span names (a misspelled northstar.claim.submit isn't flagged). Behaviour tests cover both: test_policy_denial.py, test_human_in_the_loop.py, test_demo_flow.py, test_registry_live_check.py.
  • gen_ai.* can't be referenced. semconv v1.44.0 excludes gen_ai.* from dependency resolution, so the decision span uses the owned northstar.policy.tool.name, not gen_ai.tool.name.
  • Operational cost. Live-check keeps every sample: about 3.8 MB/min on an idle demo cluster, limit 4Gi (≈17 h). It also clones semconv from GitHub on every start, so it needs egress. Fine for a gate, not for a long-lived production sidecar as-is.

Alternatives

  • Constants in code only (a shared module of attribute names). Stops typos within one language; no cross-language docs, no live check.
  • Backend-side schema (tests or dashboards that fail on missing fields). Catches drift late, after the data is already wrong.
  • Collector processors (transform, attributes) to rename at ingest. Hides drift instead of fixing it, and the repo's rule forbids rewriting third-party spans.
  • Proposing upstream conventions. The long-term fix for decision spans; Weaver is also how upstream semconv itself is defined, so a registry like this is a ready draft.

If someone asks

Does Weaver validate gen_ai.* too?
Not here. Standard names show up as "not in registry" at information level; only ours fail the gate.
Does live-check run in production?
In this demo it runs in-cluster as a gate. Its unbounded memory makes it a CI/staging tool today rather than an always-on production component.
