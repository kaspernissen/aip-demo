The call graph is no longer something you drew

KASPER · starts 23:50 · 45 s

Manuscript

KASPER

Why does an agent need all this more than a normal service? In a normal system you can draw the call graph, the map of who calls whom, on a whiteboard before it runs.

[point at the prompt on the left, then each run]

An agent is different. One prompt: "settle this car-damage claim". The same prompt, run three times. Run one reads the claim, then pays. Run two reads the claim and stops to ask a human. Run three checks the policy instead of the claim, and pays. And the orange bars underneath are the tokens each run used, so even the cost changes.

It's like a taxi driver who picks a new route every ride. The code tells you what the agent may do, not what it will do. A test that passed on run two tells you nothing about run three.

"The model draws the call graph at run time."

So if you can't draw the path in advance, you record it as it happens. Here's what got recorded for the Large claim.

What the slide is for

It justifies the whole Trace half. Platform engineers know tracing from microservices; this slide says what is new with agents. For a microservice, the call graph is a property of the code: you can read it, test it, draw it. For an agent, the code only defines the set of tools, and the model picks a path through them at run time. So the trace stops being a debugging aid and becomes the only reliable record of what happened. That leads straight into "The audit trail is a trace".

The theory behind it

Plain version. An agent is a loop: the model reads the situation, either answers or asks to call a tool, the tool result goes back to the model, and the loop repeats until the model stops. Which tools it calls, in which order, and how many turns it takes, are decided by the model each time. Models are sampled, so the same input can give different outputs, and the inputs themselves (customer text, tool results) vary.

Consequences for operations.

  • Testing gives evidence about paths, not guarantees. A passing test covers the path it saw. Coverage of an agent is statistical: you need many runs, and you need to grade each run (that is what slides 35 and 36 do).
  • Cost and latency vary per request. Each extra model turn adds input and output tokens. The chat span records gen_ai.usage.input_tokens and gen_ai.usage.output_tokens per call, so cost per run is measurable after the fact.
  • Static architecture diagrams are no longer authoritative. The only accurate call graph is the observed one. That is why Northstar never samples: a run you dropped is a path you never saw.

In OpenTelemetry terms, each box in the figure is a span: chat for a model turn, execute_tool <name> for a tool call, all under one invoke_agent span. The three runs would be three traces with different shapes. Slide 34 names these spans properly.

Configuration and options

  • The figure is illustrative (book Ch 1, relabelled to a claim settlement). Northstar's real settlement path is constrained: the settlement agent has three tools, propose_payment, execute_payment and refuse_payment, and the evaluator took_a_known_path checks the order afterwards.
  • Variance can be narrowed (lower temperature, fewer tools, structured outputs, a deterministic workflow around the agent, which is William's "deterministic spine"), but not removed while a model chooses the next step.
  • Sampling: no sampler in any SDK or in the collector; agentgateway sets randomSampling: true so even a headerless caller is traced.

Alternatives

  • Constrain the agent into a fixed workflow (a state machine where the model only fills in values). Makes the graph drawable again, at the cost of the flexibility that made an agent worth using. Northstar does this partly: the workflow owns propose, decide, pay.
  • Log-based recording of prompts and tool calls. Captures content, but loses causality across services: you can't see which tool call caused which downstream request without a shared trace id.
  • Replay/eval harnesses offline. Useful before release, but they test the runs you thought of, not the ones that happened in production.

If someone asks

Isn't this just non-determinism, which we already handle with retries and timeouts?
Retries handle a known path failing. Here the path itself changes. You can't put a timeout on a step you didn't know would happen.
Does setting temperature to zero fix it?
It reduces variance for identical inputs, but inputs differ every time (customer text, tool results), and providers don't guarantee bit-identical outputs at temperature zero.
Is the token bar real data?
No, it is illustrative. The real numbers per call are on each chat span in Jaeger.
