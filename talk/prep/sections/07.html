Authority accumulates

WILLIAM · starts 2:50 · 45 s

WILLIAM

How does an agent end up able to do more than anyone chose? Not through one big decision. Through small ones nobody remembers making.

A tool gets added for one workflow, and it stays available for every workflow. A credential gets scoped for a demo, and it survives into production. A delegation gets added to unblock a Friday deploy, and it becomes a permanent edge in the graph.

[point at the box on the right]

On the right is what the agent's tools and credentials allow. The part anyone actually decided is that small box. Everything around it, the hatched area, nobody decided.

Nobody decided to give the agent that reach. The agents behave. The boundaries erode anyway.

What the slide is for

It explains how the gap from slide 3 appears, so the audience recognises it in their own systems. The key phrase is "the agents behave": this is not about a rogue model. Even a perfectly obedient agent ends up with authority nobody chose, because authority is granted in small, local, reasonable steps and never taken away. That makes it a platform problem, not a model problem, which sets up slides 8 and 9.

The theory behind it

Plain words. It is the same as permission creep for people: someone changes teams and keeps their old access. Each grant was sensible when made. The total is something nobody would sign off on if asked directly.

Why agents make it worse.

  • Tools are shared across tasks. An MCP server exposes a list of tools (tools/list) and the model may pick any of them on any run. A tool added for workflow A is visible in workflow B unless something filters it.
  • Credentials are ambient. If the agent process holds an API key or a broad token, every tool call carries it. Long-lived static secrets outlive the demo they were made for.
  • Delegation graphs grow. With agent-to-agent protocols (A2A), agent X may hand a task to agent Y. Each new edge extends what X can cause, transitively.
  • Nobody reviews the union. Reviews look at one change at a time. The effective authority is the sum of all of them, and it is rarely computed.

Security standards name this as Excessive Agency (OWASP LLM06) and recommend "least agency". The practical point: authority has to be declared somewhere a reviewer can see it whole, and enforced against that declaration, rather than accumulated in code and config scattered across teams.

Alternatives

Periodic access reviews and entitlement tooling (the identity-governance approach) find accumulated access after the fact. Policy-as-code with deny-by-default (OPA/Gatekeeper, Kyverno, Cedar, CEL in gateways) prevents it up front. Most teams need both: deny-by-default for agents, and a review process for what the allowlists contain.

If someone asks

Isn't this just RBAC hygiene?
Partly. RBAC covers the Kubernetes API. An agent's authority also lives in tool lists, API keys, network paths and delegation edges, which RBAC doesn't see. The rings on slide 11 cover each of those.
