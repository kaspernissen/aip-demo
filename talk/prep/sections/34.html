The gen_ai.* names: what a trace can say

KASPER · starts 30:30 · 60 s

Manuscript

KASPER

So how do you describe what an agent did, in telemetry? OpenTelemetry has a set of names for it: the gen_ai semantic conventions. Three span types carry the agent's work.

[left card]

invoke_agent: an agent takes a task. It names the agent, and the conversation id. Here that's the claim id, so every trace of one claim belongs together.

[middle card]

chat: one call to the model. Which model, how many tokens, and the finish reason: did the model answer, or ask to use a tool?

[right card]

execute_tool: the agent uses a tool. Which tool, and a call id that ties it back to the model's request.

[the legend]

The solid names are recorded by default, and they already tell you what the agent did. The dashed ones are the content: the system prompt, what the model was told and answered, the tool's arguments and result. That's the most sensitive data, so the spec makes it opt-in. We turn it on, because it's exactly what explains why. You saw it in the demo.

"By default, the trace says what the agent did. With content on, it also says why."

What the slide is for

It gives the audience the vocabulary the next two slides depend on. Evaluation (slide 35) asks questions of these spans; AgentEvals (slide 36) reads them. Without this slide, "read from execute_tool spans" means nothing to a newcomer. It also plants the trade-off every regulated team has to decide: content capture.

The theory behind it

Plain words. HTTP spans have had standard names for years (http.request.method, http.response.status_code), which is why any backend can draw a latency chart for any web service. The gen_ai conventions do the same for model and agent calls, so a tool like AgentEvals, Phoenix or Langfuse can read an agent it has never seen.

Conversation id = claim id. Both agents set gen_ai.conversation.id to the claim id. That one choice is what lets AgentEvals group the intake (claims-agent) and the settlement (settlement-agent) into one session, even across traces.

Who emits them. PydanticAI's instrumentation in both agents emits these spans. agentgateway also writes a span per model call with the same gen_ai names plus jwt.sub and cost. Trap: summing tokens across every span counts each call twice. Pick the agent's chat spans or the gateway's.

Configuration and options

  • One switch: NORTHSTAR_CAPTURE_CONTENT, read by capture_content_enabled() in each agent's bootstrap.py and passed to PydanticAI's InstrumentationSettings(include_content=...). Deployed "true" in deploy/k8s/settlement-agent.yaml and claims-agent.yaml. Unset = on; false/0/no/off = off.
  • What off loses (measured): the gen_ai layer shrinks from 28 to 25 distinct keys; message text, tool arguments and results disappear. The platform's evidence (northstar.policy.*, northstar.review.*, claim id) is unchanged. What's lost is the model's own account: independent corroboration of the requested amount, what it was told about this claim, and what the ledger said back.
  • Collector-side redaction is the middle path: keep emitting, hash or drop sensitive attributes in an attributes processor before the backend. Not built in the repo.
  • Never removed: model_request_parameters (static instructions and tool schemas, no claim data) and gen_ai.tool.definitions.

Alternatives

  • OpenInference (Arize's convention): older, widely used by Phoenix; overlaps with gen_ai and maps to it.
  • Vendor SDK traces (Langfuse, LangSmith native SDKs): rich, but tie your telemetry to one backend.
  • Store content outside the trace (object store, referenced by id), with its own access control. The conventions recommend this for sensitive content.

If someone asks

Isn't gen_ai.system_instructions deprecated?
The whole gen_ai namespace moved out of the core semantic-conventions repo into open-telemetry/semantic-conventions-genai. Core marks every gen_ai attribute "deprecated: moved". In the new repo, system_instructions is current: development stability, opt-in.
Doesn't capturing prompts violate GDPR?
It can. That's why it's opt-in. The demo shows the trade: with capture off the governance evidence survives intact; the model's own account of itself doesn't. Engineering, not legal advice.
Verify before the talk The GenAI conventions are at Development stability; names may still move. Check the semantic-conventions-genai repo for renames the week of the talk.
