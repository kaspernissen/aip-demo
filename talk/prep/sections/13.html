SPIFFE and SPIRE

WILLIAM

The core first: who is acting. Everything after this keys off it. So, one minute on the two projects that answer it, with one picture: a passport.

[left]

SPIFFE is the standard: what a passport looks like. An ID for a workload, not a person: spiffe, colon, slash slash, northstar dot local, the namespace, the service account. And the document that carries it, the SVID: short-lived, and signed.

[right]

SPIRE is the passport office. It runs an agent on every node. When a pod asks for its identity, that agent checks where the pod really runs, its namespace and its service account, and only then does the SPIRE server sign.

[the four boxes, left to right]

Four steps. The pod asks, over a local socket, with no secret. SPIRE checks. SPIRE signs something that expires soon and renews on its own. And the pod shows that passport at the gateway, on every call.

And the agent card an agent publishes? That's the brochure, not the passport. Anyone can print a brochure.

No password to leak. The identity is proven by where it runs, not by what it says.

What the slide is for

Every later check uses the caller's identity as an input: the gateway's CEL rule, the model allowlist, the flag targeting, the decision table, the keystone. If identity were a name the agent could claim, every one of those would be decoration. This slide gives the audience the vocabulary (SPIFFE, SPIRE, SVID, attestation) in plain terms before the config slide.

The theory behind it

Plain words. A password proves you know something, and anything you know can leak. Attestation proves where you are: the node agent asks the kernel which process is calling, then asks the kubelet which pod and service account that process belongs to. Nothing secret sits in the pod to be stolen.

The pieces.

  • SPIFFE ID: a URI, spiffe://<trust domain>/<path>. Northstar's path is /ns/<namespace>/sa/<service account>.
  • SVID (SPIFFE Verifiable Identity Document): either an X.509 certificate (for mTLS) or a JWT (a bearer token with an audience). Northstar uses JWT-SVIDs to call the gateway.
  • Workload API: a Unix socket on the node. The SPIFFE CSI driver mounts it into the pod; the agent calls it and gets an SVID back.
  • Trust bundle / JWKS: the public keys a verifier uses. The gateway fetches them from SPIRE's OIDC discovery provider.

Why the audience matters. A JWT-SVID is minted for one verifier: aud = spiffe://northstar.local/ns/northstar-platform/sa/agentgateway. Stolen and replayed against a different service, it fails. Expiry limits the window further; agents/settlement-agent/svid.py refreshes a cached token when less than 30 seconds of life remain, so an in-flight expiry is not mistaken for an identity failure.

Configuration and options

  • Trust domain: northstar.local, set in deploy/platform/spire/values.yaml under the chart's global.spire block (a root-level trustDomain: is silently ignored by the umbrella chart).
  • Selectors: k8s:ns and k8s:sa. More are available (k8s:pod-label, k8s:container-image, node attestation by cloud instance identity) if a team wants identity tied to the exact image too.
  • SVID lifetime: SPIRE's server default for JWT-SVIDs is short (minutes); the chart can set defaultJwtSvidTTL and defaultX509SvidTTL. Northstar leaves the chart default.
  • Telemetry: SPIRE has no OpenTelemetry tracing; server and agent expose Prometheus metrics on 9988. The identity shows up downstream as jwt.sub on the gateway's span and northstar.policy.caller.spiffe_id on the decision span.

Alternatives

  • Projected ServiceAccount tokens: audience-bound and short-lived, no extra system. Kubernetes-only, and the only attestation is "the API server says so".
  • Mesh identity (Linkerd, Istio): mTLS certificates from the ServiceAccount. Proves the TCP peer, but it isn't a credential in the request, so a gateway can't easily hand it to a policy engine. Istio's IDs are SPIFFE-formatted.
  • Cloud workload identity (EKS Pod Identity/IRSA, GKE, Azure): good for cloud APIs, vendor-specific.
  • cert-manager csi-driver-spiffe: SPIFFE X.509 SVIDs without SPIRE's attestation model.

If someone asks

Why JWT and not mTLS SVIDs?
The gateway needs the caller in the request so it can pass it to CEL and to the decision service as jwt.sub. A JWT is a bearer token, so audience and expiry are what limit replay; binding it to the TLS connection is recorded in docs/architecture.md as later hardening.
Does every service hold an SVID?
No. It's enforced on the hops into the gateway (settlement-agent and reviewer-ui for tools, both agents for the model). The tool and the ledger rely on Linkerd's mesh identity (slide 15).
What's wrong with the agent card?
An A2A agent card is self-published metadata. Northstar's cards (contracts/agent-cards/*.json) carry no identity binding, so they describe, they don't prove.
Verify before the talk SPIFFE and SPIRE graduated in the CNCF in 2022. Check the JWT-SVID TTL default for SPIRE 1.15 if anyone is likely to ask for the number.
