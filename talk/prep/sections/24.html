"Every line of config you saw has a line of output like this."

Every one of those answers came out of a trace. So why does an agent need one, more than any other service?

What the slide is for

The demo moves fast and the terminal output is small. This slide freezes the three outputs that matter and labels each with the ring it belongs to, so the audience can connect what they just saw to William's model. It closes the loop on the promise "you'll see this again in the demo" from slides 8, 16 and 18, and gives the auditor's second question (who allowed it, within what limits?) its answer on one screen: a rule, a limit, a caller. It is also the pivot from Decide to Trace: the last sentence sets up why agents need tracing more than ordinary services.

The theory behind it

Two independent "no"s. The left and middle panels are two different kinds of refusal. The flag panel is a contextual decision: it depends on who is asking, today's autonomy level and the ledger, so the gateway asks the policy service. The ceiling panel is a static invariant: no payment above €50,000, whoever asks, written as one CEL expression in the gateway. CEL can't look things up, so it holds only facts that never change. Because the ceiling refuses before the remote guardrail runs, "policy service never asked" is literally true: there is no northstar.policy.decision span for that call.

Defence in depth against prompt injection. The model ignoring the instruction is good behaviour, but behaviour is probabilistic. The ceiling is deterministic. The demo tests both layers separately: inject first reads what the model did (from the chat span), then sends the worst case anyway, so the second layer is proven even when the first one held.

Identity as the shared key. The right panel is a decoded JWT-SVID. sub is the SPIFFE ID SPIRE minted from namespace and service account. aud is the gateway's own SPIFFE ID, so a token stolen from this hop is useless anywhere else. The CEL rule, the PDS rule lookup, the flag targeting and the span attribute jwt.sub all use that same string.

Configuration and options

- allow: 'jwt.sub in [".../sa/settlement-agent", ".../sa/reviewer-ui"]
   && (mcp.tool.name != "execute_payment"
       || (mcp.tool.arguments.amount > 0
           && mcp.tool.arguments.amount <= 50000))'
  • Limit table: platform/policy-decision-service/pds/rules.py, EXECUTE_LIMITS, keyed by (caller, level): assisted 0, autonomous 6000. No row means deny (unknown_caller).
  • Rule name on the span: northstar.policy.rule = settlement-agent.autonomous.execute_limit; a human release uses human-approved.execute.
  • The commands behind each panel: scripts/demo evidence (left), scripts/demo inject / ceiling (middle), scripts/demo guard (right, decodes the SVID, never prints the token).

Alternatives

  • Put the ceiling in the PDS too: one place for all rules, but then a PDS bug or outage could affect the hard limit. Keeping it in the gateway means the ceiling holds with no network call.
  • Put the €6,000 limit in CEL: possible for a single fixed value, but it would need a gateway config change to move it and could not read the flag or the ledger.

If someone asks

Why is the 403 at the gateway and not a PDS deny?
Two ways to say no. The ceiling is a fixed invariant, so it lives in CEL and is checked first. The limit depends on caller and level, so it needs a lookup.
Is the decision span an error when it denies?
No. A deny is the platform working; the span status stays Unset. The refused execute_tool span on the agent side is the one shown in red.
Could someone replay the token?
The SVID is short-lived and audience-bound to the gateway; the mesh also carries mTLS on every hop.
