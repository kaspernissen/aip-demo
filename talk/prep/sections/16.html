One door, three checks

WILLIAM · starts 10:40 · 55 s · Ring 2 · per call

Manuscript

WILLIAM

agentgateway is the only door to the tools, and in a moment, to the model. For a tool call: three checks, in order, all in one config file.

[check 1]

One: the passport. No valid SPIFFE token: 401.

[check 2]

Two: one CEL rule. Only two workloads may use the tools at all: the settlement agent, and the reviewer UI when a person releases a payment. Anyone else, even with a valid passport: 403. And execute_payment above fifty thousand euros is refused. Always. Whoever asks.

[check 3]

Three: everything else goes to the policy service. And if the policy service can't answer, the answer is no. Fail closed.

Why two ways to say no? CEL is fast and needs no code, but it can't look anything up. So it holds the facts that never change. The everyday limit depends on who's asking, how much we trust them today, and what the ledger says. That needs a lookup, so the gateway asks.

CEL for what the request proves. Ask when the answer needs a lookup.

What the slide is for

This is where intent meets capability. Whatever the model was told, the call it makes is checked here. The slide sets up two moments in the demo: the €80,000 call refused by CEL alone (slide 24, "the policy service was never asked"), and the €8,500 call refused by the policy service (the held claim). It also teaches the PEP/PDP split: the gateway enforces, the decision service decides.

The theory behind it

Plain words. The bouncer checks your ID at the door and knows one house rule by heart: nobody carries more than €50,000 in. For anything that needs judgement ("is this guest's tab within their limit tonight?") he phones the manager and does what she says. The bouncer is the policy enforcement point; the manager is the policy decision point.

CEL (Common Expression Language) is a small, side-effect-free expression language, also used by Kubernetes admission and Kyverno. It can read what's in the request: jwt.sub, mcp.tool.name, mcp.tool.arguments.amount. It can't call out, so it can't know today's autonomy level or the payment's ledger state.

Why an allow rule, not a deny rule. If a CEL expression errors (amount is a string, or missing), an allow rule doesn't match, so the call is denied. A deny rule that errors is skipped, which fails open: in the CEL spike the string "6200" went through a deny rule and the payment executed. Write ceilings as allow rules.

"HTTP 200 means no." When the PDS denies, agentgateway v1.6.0 answers with an ordinary MCP tool result marked isError: true on HTTP 200, carrying a tag like [policy-denial rule=settlement-agent.autonomous.execute_limit limit=6000 requested=8500]. The model reads it as a tool that said no and explains it to the customer. A dashboard counting 5xx sees success. The trace is where the refusal is unmistakable.

Configuration and options

# deploy/platform/agentgateway/config.yaml (port 3000, condensed)
jwtAuth: { mode: strict, issuer: …spire-spiffe-oidc-discovery-provider…,
           audiences: [spiffe://northstar.local/ns/northstar-platform/sa/agentgateway],
           jwks: { url: …/keys } }
authorization: { rules: [ allow: 'jwt.sub in [settlement-agent, reviewer-ui]
   && (request.method != "POST" || mcp.methodName != "tools/call"
       || mcp.tool.name != "execute_payment"
       || (mcp.tool.arguments.amount > 0 && mcp.tool.arguments.amount <= 50000))' ] }
mcpGuardrails: { processors: [ { kind: remote, methods: {"tools/call": request},
   host: policy-decision-service…:9100, failureMode: failClosed,
   metadata: { caller: 'jwt.sub' },
   requestHeaders: { allowed: [traceparent, tracestate] } } ] }
  • jwtAuth.mode: strict (no valid token: 401), optional (validate if present), permissive. Wrong audience, expired or forged: 401, span reason=JwtAuth, the PDS is never called.
  • failureMode: failClosed or failOpen. One word turns a PDS outage into "everything allowed". Northstar's tests pin it.
  • metadata.caller: 'jwt.sub': the verified subject is handed to the PDS. Identity is an input to the decision, not a label on it.
  • requestHeaders.allowed: forwards traceparent so the decision span lands in the same trace.
  • The remote guardrail speaks agentgateway's ExtMCP gRPC protocol (/agentgateway.dev.ext_mcp.ExtMcp/CheckRequest).
  • Not used: the built-in mcpAuthorization (it hides denied tools from tools/list but can't see arguments), rate limits, A2A routes. Tracing is never sampled: randomSampling: true.

Alternatives

  • Gateways: Agent Router (formerly Envoy AI Gateway; CEL MCP authorization, fails closed since v1.2), Kong AI Gateway (MCP tool ACLs, Enterprise), IBM ContextForge, LiteLLM.
  • Decision engines behind the gateway: OPA/Rego (CNCF graduated; can pull external data), Cedar (analysable policy language; agentgateway has an integration), OpenFGA or SpiceDB for relationship-based checks. Northstar's PDS is ~275 lines of Python so the rule is readable on one screen.
  • All in CEL: possible only if the limit never depends on a lookup. Here it does (flag + ledger).

If someone asks

What if the policy service is down?
Fail closed: the call is refused. A Guardrail span with a non-zero gRPC status tells "the service was down" apart from "the policy said no" (gRPC status 0 plus a deny decision span).
Can I hot-reload the CEL?
The config is a ConfigMap; the reload took about 55 s in the spike (kubelet propagation). Too slow for a live edit on stage; fine for GitOps.
Does the ceiling stop prompt injection?
Only above €50,000. An injected amount under the ceiling goes to the PDS like any other amount; the PDS checks the limit and the ledger, not what the customer wrote.
Verify before the talk The jwtAuth modes other than strict (optional, permissive) are listed from the agentgateway docs, not tested on Northstar. Check them against the v1.6.0 docs.
