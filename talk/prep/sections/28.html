Two protocols, two jobs

KASPER · starts 26:20 · 55 s · cut first for 30 min

Manuscript

KASPER

Two protocols carried every hop you just saw.

[left]

On the left, MCP, the Model Context Protocol. It reaches down, from an agent to a tool. The agent asks the tool server what it can do: tools/list. The server answers with its tools. The model picks one and calls it, here execute_payment with an amount, and gets a result back. Call, answer. That's it.

[right]

On the right, A2A, Agent2Agent. It reaches across, from one agent to another. First the claims agent reads the other agent's card: who are you, what can you do, where do I find you. Then it hands over a task: settle this claim. And the task has a life: working, then input required while it waits on someone, then completed.

The platform questions differ. For MCP: which tool, which arguments, who is asking? For A2A: who may delegate to whom, and does the original identity survive the hand-off?

"Both open, both in the Agentic AI Foundation. Neither one decides what an agent may do."

That's the platform's job. And neither protocol carries the trace for you. So how did one trace id get across all of it?

What the slide is for

It names the two protocols the trace has to cross, in the simplest form that is still correct, and plants the key line: protocols connect, they don't govern. It is the first slide to cut for a 30-minute slot; if cut, slide 29 still works because it names each hop's protocol.

The theory behind it

MCP (Model Context Protocol). JSON-RPC 2.0 messages between a client (inside the agent) and a server that exposes tools, resources and prompts. Northstar uses the streamable HTTP transport. The lifecycle is initialize, then tools/list (discover), then tools/call with {name, arguments}. The model never talks to the server; the agent's code turns a model's tool request into a tools/call. That is the point where a gateway can sit and read the tool name and arguments, which is exactly what agentgateway's CEL rule (mcp.tool.name, mcp.tool.arguments.amount) uses.

A2A (Agent2Agent). Also JSON-RPC over HTTP, between peers. A server publishes an agent card (name, skills, endpoint URL, supported features). A client sends a message that creates a task; the task moves through states (submitted, working, input-required, completed, plus failed, canceled, rejected). Results come back as messages and artifacts, by polling, streaming or push notification. In Northstar, the held Large claim sits in input-required while a person decides, and the outcome is pushed back to the customer's page.

Why "neither decides". MCP has an authorization spec for authenticating the client to the server (OAuth-based), and A2A cards can declare security schemes. Both answer "can this client connect", not "may this agent pay €8,500 today". Per-call business authorization has to live outside the protocol, at the gateway and the decision service.

The agent card is a brochure, not a passport. Anyone can publish a card claiming any name. Northstar's identity comes from SPIFFE, not from the card (contracts/agent-cards/*.json carry no identity binding).

Configuration and options

  • MCP: mcp==2.2.0 client in settlement-agent, FastMCP 4.0.3 server in payments-mcp (tools propose_payment, execute_payment, refuse_payment, get_payment). The client opens a fresh session per call, so each tool call is MCP send initialize plus MCP send tools/call <tool>.
  • A2A: a2a-sdk==0.3.7 on both agents; delegation is configured explicitly in agents/claims-agent/delegation.py, never discovered at run time.
  • A2A's own spans carry almost no attributes (no task id, no context id); see the telemetry contract's Gap 1. Northstar uses gen_ai.conversation.id = claim id instead.

Alternatives

  • Plain REST/gRPC between agents and tools: works, but loses tool discovery and the shared vocabulary that lets a gateway understand calls generically.
  • Framework-internal tools (PydanticAI or LangChain function tools) with no protocol: simplest, but nothing sits between the model's request and the side effect.
  • Message queues for agent hand-off: durable, but no standard task lifecycle or card.

If someone asks

Does MCP's OAuth authorization replace the gateway?
No. It authenticates the client to the server. It doesn't express "amounts over €6,000 need a person at this autonomy level".
Why A2A between two agents in the same cluster?
It makes the hand-off a governed, traced protocol hop with a task lifecycle, which is how the "input required" wait and the push back to the customer work.
Are you on A2A v1.0?
No, a2a-sdk 0.3.7. The 1.x SDK (protocol v1.0) exists; per the repo's notes it still has no trace propagation code.
Verify before the talk MCP and A2A both in AAIF (A2A joined 2026-08-17, secondary source), the week of the talk. A2A task state names include working, input-required, completed in the spec version shown.
