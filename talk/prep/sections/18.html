One flag, one table

WILLIAM

Ring two has a second half: how free is the agent today? That's a live setting, its autonomy level, and it's a feature flag. OpenFeature is the CNCF standard for asking about feature flags. The question is standard; what answers it is pluggable. Like a wall socket: every appliance fits the same socket, whatever power station is behind it.

[left column, top to bottom]

Where the level lives: a FeatureFlag, a plain Kubernetes object. flagd, the provider, serves it as a sidecar. And the decision service asks one question through the OpenFeature SDK: what's the autonomy level for this SPIFFE ID? The caller comes from the passport on the call.

[right column]

The config. The flag gives one value to one identity, the settlement agent. The default is assisted; Kasper's demo sets it to autonomous. Under it, the policy service's table: assisted, zero euros, so a person signs every payout. Autonomous, up to six thousand, and above that a person decides. Any other caller has no row, and no row means deny.

[the four icons]

Why a flag for a policy knob? No deploy. A one-word diff you can review. Answered per caller. And it leaves a trace: every decision is a span with rule, limit, amount, caller and level. If flagd can't answer, the level falls back to assisted.

Same agent, same code, same image. Only the flag decides how free.

Keep one question in your head: if one value decides this much, who may change it? That's the keystone.

What the slide is for

This makes "bounded autonomy" concrete: autonomy is a number in a table, selected by one flag value per identity. It sets up the demo (the flag is at autonomous when it starts), the €8,500 hold in demo step 2 (above 6,000), the close ("Autonomy is a platform setting", slide 38), and the keystone (slide 19) by ending on "who may change it?". Demo step 5 answers that question live.

The theory behind it

Plain words. The flag says which column of the rulebook applies to this agent today; the table says what that column allows. Moving the agent from assisted to autonomous is like moving a new employee's signing limit from zero to €6,000: same person, same job, more trust, and the limit is written down.

OpenFeature is a vendor-neutral API and SDK for evaluating flags. Your code calls get_string_details("autonomy-level", default, context); a provider answers. Swap the provider and the code doesn't change. flagd is OpenFeature's reference provider; the Open Feature Operator injects it as a sidecar and feeds it the FeatureFlag CRD.

Targeting uses JsonLogic: if: [ in(spiffeId, [...settlement-agent]), "assisted", "assisted" ], i.e. if/then/else. The evaluation context carries the caller's SPIFFE ID, so the answer is per identity.

Fail closed, twice. The SDK returns the default value on a provider error; pds/autonomy.py passes "assisted" as that default and forces assisted itself whenever an error code is present, so a future SDK change can't widen authority. A flagd outage silently lowers authority; it never raises it.

Configuration and options

# deploy/platform/openfeature/featureflag.yaml (committed: both branches "assisted")
autonomy-level:
  state: ENABLED
  variants: { assisted: "assisted", autonomous: "autonomous" }
  defaultVariant: assisted
  targeting:
    if:
      - in: [ {var: spiffeId}, ["spiffe://…/sa/settlement-agent"] ]
      - "assisted"       # if[1]: scripts/demo start patches this to "autonomous"
      - "assisted"
# platform/policy-decision-service/pds/rules.py
EXECUTE_LIMITS = { (settlement-agent, "assisted"): 0.0,
                   (settlement-agent, "autonomous"): 6000.0 }
  • The table is keyed by (SPIFFE ID, level), so identity is structurally required. A miss is unknown_caller or unknown_autonomy_level: deny.
  • Rule names on the span: settlement-agent.<level>.execute_limit; the human path is human-approved.execute (reviewer-ui, only for payments the ledger shows awaiting_approval).
  • scripts/demo autonomy <assisted|autonomous> patches if[1], checks flagd resolved it, and checks no pod restarted.
  • Telemetry: the decision span records level, reason, variant and feature_flag.version; the lookup also emits a feature_flag.evaluation log record. A kubectl flip itself leaves no span (only Backstage's flip emits northstar.autonomy_contract.change).

Alternatives

  • A ConfigMap read per decision: no SDK, no targeting, no evaluation telemetry.
  • Put the level in the rule table: every change is a code change and a deploy.
  • Commercial or other OSS providers behind the same OpenFeature call: LaunchDarkly, Flagsmith, Unleash, GO Feature Flag, ConfigCat. Gains UI, audit log and approvals; adds an external dependency on the decision path.
  • Encode the limit in OPA data or Cedar policy instead of a flag: works, but then "how free today" and "what the rule is" live in the same artifact.

If someone asks

Isn't changing a flag at runtime exactly the risk?
Yes, which is why the flag is a protected object: an agent identity can't write it (Kyverno), and a person changes it through a reviewed commit.
How fast does a flip take effect?
flagd watches the CRD; the next decision uses the new level. No restart. The demo verifies that no pod restarted.
Why not more levels?
Nothing stops it: add a variant and a row. Two keep the demo legible.
Verify before the talk OFO v0.9.3 still injects flagd v0.16.2; OpenFeature still CNCF Incubating.
