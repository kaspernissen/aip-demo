And the keystone. That flag is one value on one object. So who may change it? If the answer is "the agent", every limit you've seen is a suggestion.

[the subtitle]

The objects that define the agent's authority: its flag, its permissions, the policies, the gateway routes, its SPIFFE registration.

[the two rows]

If the agent's own identity tries to change any of them: denied, at admission. A person or a pipeline, through a reviewed commit: applied. The rule itself is a few lines of Kyverno, in CEL: if the request comes from a service account in the agents' namespace, deny.

And it holds when someone makes a mistake. Grant the agent the permission by accident, so RBAC says yes, and Kyverno still says no. Kasper ends the demo on exactly that.

Even when RBAC says yes, Kyverno says no.

What the slide is for

It answers the question slide 18 ended on, and it's the clasp of the Safe Operating Model: an agent that could edit its rings has no rings. It also sets up demo step 5 (scripts/demo keystone), so the audience knows what "RBAC says no, then Kyverno says no" will mean when they see it.

The theory behind it

Plain words. RBAC is the list of keys someone has been given. Admission control is a guard at the door who checks every change regardless of keys. Mistakes happen in RBAC (one wide RoleBinding, one copied ClusterRole); the keystone exists for that day.

How admission works. Every write to the Kubernetes API passes authentication, then authorization (RBAC), then admission webhooks, then storage. Kyverno registers a validating webhook. Its ValidatingPolicy type uses CEL, the same shape as Kubernetes' built-in ValidatingAdmissionPolicy, with Kyverno's reporting and exceptions on top.

Two walls, in order. First, RBAC grants agent ServiceAccounts no writes at all. Second, the keystone denies writes from agent identities even if RBAC is loosened. The demo proves the second wall by deliberately over-granting patch on the flag (deploy/demo/keystone-overgrant.yaml), then removing it on every exit path.

Configuration and options

# deploy/platform/kyverno/keystone-policy.yaml (condensed)
kind: ValidatingPolicy            # policies.kyverno.io/v1
metadata: { name: agents-cannot-edit-their-own-authority }
spec:
  validationActions: [Deny]
  failurePolicy: Fail
  matchConditions:
  - expression: request.userInfo.username.startsWith('system:serviceaccount:northstar-agents:')
             || request.userInfo.username.startsWith('system:serviceaccount:northstar-tools:')
  validations:
  - expression: "!variables.isProtected"
  • Protected objects (CREATE/UPDATE/DELETE): FeatureFlags and FeatureFlagSources in northstar-platform; the agentgateway-config ConfigMap; pods, namespaces; deployments, replicasets, statefulsets, daemonsets; jobs, cronjobs; NetworkPolicies; every Linkerd policy kind; HTTPRoutes; SPIRE's ClusterSPIFFEID, ClusterStaticEntry and federation CRDs; Roles, RoleBindings and their cluster forms; every Kyverno policy kind; and CREATE of serviceaccounts/token.
  • failurePolicy: Fail: an unreachable Kyverno refuses matched writes. The flip side: a graceful Kyverno stop deletes its own webhook registrations, after which the keystone is silently off while the policy object still exists. scripts/preflight.sh checks the registration, not just the policy.
  • The slide shows one prefix; the file also matches northstar-tools.
  • validationActions could be [Audit] or [Warn] for a dry run before enforcing.
  • Kyverno v1.19 deprecates the legacy ClusterPolicy (kyverno#16868); this uses the CEL-based type.

Alternatives

  • ValidatingAdmissionPolicy (built into Kubernetes, GA in 1.30): the same CEL rule, evaluated in the API server, no webhook to run or to lose. Lacks Kyverno's reports, exceptions and telemetry.
  • OPA Gatekeeper: Rego-based admission; strong if you already run OPA.
  • Kubewarden (CNCF sandbox): policies as WebAssembly modules.
  • Tight RBAC alone: necessary, and the first wall here, but one mistaken binding opens everything.

If someone asks

What about an agent with node or shell access?
Out of scope. The keystone guards the Kubernetes API only; anything that edits state outside the API isn't covered.
How do you know the denial came from Kyverno and not RBAC?
The message names the webhook and the policy. One test once passed for the wrong reason: kubectl annotate reads before it patches, so RBAC refused the read and Kyverno never saw the write. The over-grant now includes get.
Who can change the flag, then?
Humans, CI and the platform's own writer identity, through a reviewed commit. Anyone outside the agents' and tools' namespaces is not matched.
